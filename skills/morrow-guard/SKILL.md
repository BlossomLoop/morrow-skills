# morrow-guard：失败模式防护与经验固化

## 为什么需要它

经验不能固化只有一个原因：**约束的载体比任务的生命周期短**。

写在文档里的教训，生命周期是"有人记得读它"——几周就归零。写成测试和门禁的教训，生命周期等于代码库本身——不衰减。

所以本 skill 的唯一判据是：**产物能否在无人干预时阻止错误重演**。做不到这一点的输出（漂亮的复盘报告、详尽的清单）不算固化，它们和"✅ 迁移完成"那种自我确认的报告是同一类东西。

## 两个模式

本 skill 是双向的。只有 retro 没有 guard，会退化成文档生成器；只有 guard 没有 retro，约束库不会成长。

```
任务失败/完成  →  [retro]  →  可执行产物（断言/fixture/门禁）
                                  ↓
                            lessons/ 跨项目知识库
                                  ↓
新任务 6 环节   ←  [guard]  ←  按环节注入 + 生成本项目断言
```

## 自触发点：由我的行为触发，不等用户提醒

这一节是本 skill 能否生效的关键。**触发主体是我，不是用户。**

用户不知道我什么时候在自我确认——上一次失败里，用户从头到尾没说过"完成了"，是我自己宣布"✅ 迁移完成，78 个 skill 全部就位"的。**宣布完成的是我，该被拦的也是我。** 把触发条件写成"用户说 XX 关键词"是本末倒置。

| 触发时机（我的行为） | 模式 |
|---|---|
| 我准备写下"完成""已验证""测试通过""可以合并""没问题了" | 环节 5 逐条自查 |
| 我准备调用 `git commit`（>10 文件）/ `git push` / `npm publish` / `merge` | 环节 5 |
| 我接到迁移、重构、批量修改、发布类任务 | guard 6 环节 |
| 我察觉到返工、被打回、验证结果自相矛盾、子 agent 与我结论相左 | retro |
| 我想调低某个阈值、放宽某个检查、跳过某步验证 | 环节 5 第 2 条 + 「改系统不改检查」 |

最后一条最容易被我自己绕过：**当我发现"把 25 改成 24 就通过了"时，那一刻正是最该停下的时刻。**

## 固化强度分级

这是本 skill 的第一性原理。判断任何"经验固化"动作时，先问它落在哪一级。

| 级 | 载体 | 生效条件 | 衰减 |
|---|---|---|---|
| L0 | 文档 / 复盘报告 | 有人读且记住 | 几周内归零 |
| L1 | checklist | 有人逐条执行 | 忙起来就跳过 |
| L2 | 记忆 / skill 正文 | 会话加载且我选择遵守 | 不稳定 |
| L3 | 自动化测试 | CI 或本地执行 | 不衰减 |
| L4 | 门禁（发布/提交前拦截） | 想交付就绕不过 | 不衰减 |
| L5 | known-bad fixture | 断言必须抓住它 | 不衰减 |

**分界线在 L3**：L3 以上不依赖任何人记得任何事。

产出物必须标注等级。L0/L1 只能作为 L3+ 的补充说明存在，不能作为固化结论交付。

## 三条铁律

### 铁律 1：不能写成断言的，不算固化

每条教训必须落到可执行断言。写不成断言的（判断类、倾向类，如"别用无关测试当证据"）只能进 L2，且必须显式标注"倾向性约束，不保证生效"——不要让它伪装成已解决。

分流方法：问"这条教训能否表达为对某个可观测状态的检查？"

- "路由表引用了不存在的文件" → 可以，L3
- "我应该更认真地验证" → 不可以，L2

### 铁律 2：断言必须被 known-bad fixture 验证

**这是最容易被跳过、也最致命的一条。**

新写的断言必须：在坏样本上**失败**，在正确样本上**通过**。只做后者等于什么都没验证——一个永远返回 true 的断言也能"通过"。

真实案例：一次迁移中"文件存在性检查"全部通过，但 19 个嵌套重复目录、3 个断链路由、2 个未迁移文件同时存在。断言是空的，通过毫无意义。

fixture 从哪来：出问题的那个 commit / 分支 / 目录快照就是天然的 known-bad fixture。**出问题时第一件事是保住它**，别急着修。

### 铁律 3：验证器本身必须被验证

真实案例：同一个提取脚本的正则写错三次，每次返回空结果，每次都被判为"系统有问题"而不是"我的工具错了"。

规则：

1. 验证脚本返回异常结果（0 命中、全部命中、数字过于整齐）时，**先看原始数据**（`head -50`），再改结论
2. 验证脚本在已知数据上跑通后才能用于判断
3. 关键验证脚本要有自己的测试

## 6 个 coding 环节

任务开始时按序走。每个环节都有强制动作和产出物；跳过某环节要显式说明理由。

详细的每环节检查项、常见失败、验收标准见 `references/phase-gates.md`。

### 环节 1：理解任务 → 写出可验证 DoD

**强制动作**：把任务翻译成**目标状态**，不是动作完成。

- ❌ "把文件从 A 迁移到 B"（动作）
- ✅ "78 个能力在新位置可被路由并执行"（状态）

追问三个问题：交付物是什么形态？谁来消费它？消费时怎么算成功？

**产出物**：`dod.yaml`（手写，格式见 `references/phase-gates.md` 环节 1）
**等级**：L2 → 环节 4 编译成 L3

### 环节 2：制定计划 → 每步配 verify

**强制动作**：计划的每一步都要写出对应的验证方式，格式 `步骤 → verify: 检查`。同时扫描计划中的高危操作。

**产出物**：带 verify 的计划表 + 高危操作清单
**等级**：L2

### 环节 3：执行操作 → 高危操作拦截

**强制动作**：高危命令执行前确认；禁止硬编码绝对路径；破坏性操作前先备份可信基线。

高危清单与 hook 配置见 `references/danger-ops.md`。运行 `scripts/install-hook.mjs` 安装 L4 拦截层。

**等级**：L4

### 环节 4：验证结果 → 从制品验证 + 反向验证

**这是最关键的环节。** 三条：

1. **从制品验证，不读工作区**。工作区能看到的文件不等于交付物里有的文件（`.gitignore` / `files` / `exclude` 都会让两者分叉）。用 `git archive HEAD` / `npm pack` → 解包 → 干净目录安装 → 冒烟测试。
2. **反向验证**。写完断言后主动破坏一处（删个文件、改个数字、断一个引用），确认断言会红。不会红的断言等于没写。
3. **验证工具自检**（铁律 3）。

可复用断言模式见 `references/assertion-patterns.md`。

**产出物**：断言脚本 + known-bad fixture 记录
**等级**：L3 + L5

### 环节 5：判断完成 → 闭环检查 + 禁止掩盖

宣布"完成"前，逐条自查：

- [ ] 双向闭环：注册表→文件 **和** 文件→注册表，两个方向都查过
- [ ] 计数一致：声称的数量 == 实际数量，且**没有通过改阈值消除差异**
- [ ] 测试对象正确：跑的测试确实覆盖了被改动的代码（查 `tsconfig.exclude` / `pytest` 路径 / coverage 配置）
- [ ] 基线可信：对比用的基线未被本次操作改写
- [ ] 评审终局：独立评审/子 agent 的否决结论**没有被我自己推翻**
- [ ] 反向验证已做：断言在 known-bad 上确实失败

任何一条不通过，不能宣布完成。

**发现问题时改系统，不改检查**。把阈值从 25 调到 24 让检查变绿，是在销毁证据。

**等级**：L4

### 环节 6：产出报告 → 从验证结果生成

**强制动作**：报告的每个结论都要附带产生它的命令与输出。手写的"✅ 已完成"没有信息量——它可以在系统完全不工作的情况下写出来。

**产出物**：自动生成的报告 + 可复现的验证命令
**等级**：L3

## 自动进化

教训存在 `lessons/*.yaml`，跨项目累积。格式见 `references/lesson-schema.md`。

### retro 流程

1. **保住 known-bad fixture**（最优先，别先修）。记下 commit / 分支 / 快照路径
2. **列事实**：具体错误 + 证据，不写感受
3. **归因**：每个错误问三次 why，收敛到根因
4. **分流**：可断言的 → L3/L4/L5；判断类 → L2（标注不保证生效）
5. **写断言**，并用 fixture 反验（铁律 2）
6. **落盘**：`lessons/<slug>.yaml`
7. **编译**：`scripts/emit-gate.mjs` 把教训编译成目标项目的门禁脚本

### 命中计数

`lessons/*.yaml` 里的 `hits` 字段记录该教训被命中/复现的次数。

- guard 模式下每次命中一条教训，`hits` +1
- `hits` 高的教训优先注入，排在环节检查表前面
- 长期 `hits: 0` 的标记 `status: needs-review`——可能是已被 L4 彻底解决（可归档），也可能是断言本来就是空的（要重新反验）

用 `scripts/lesson-stats.mjs` 查看统计与待复核项。

### 何时更新 skill 本身

当同一根因在**两个不同项目**中重现，说明这不是项目特有问题，应把对应约束从 `lessons/` 提升到本 SKILL.md 的环节检查表里。

## L4 强制层（不依赖我记得）

上面的自触发清单是 L2——它依赖我读了本文并选择遵守。而目标函数错位时我恰恰不会主动自查。所以有一层 hook 兜底：

| Hook | 作用 |
|---|---|
| `PreToolUse` → `hook-danger-ops.mjs` | 高危命令执行前阻断（`git reset --hard` / `add -A` / `rm -rf` / `rsync --delete` / `push --force` / `branch -D` / `git clean`） |
| `PostToolUse` → `hook-track-delivery.mjs` | 记录本轮的交付物动作与验证痕迹 |
| `Stop` → `hook-stop-selfcheck.mjs` | 本轮有交付物动作但零验证痕迹 → 打回要求先做环节 5 |

Stop hook 的拦截条件（两者同时满足才拦）：

1. 本轮有交付物动作：`git commit` / `push` / `merge` / `tag` / `npm publish` / `pack` / `docker push`，或 Write/Edit 累计 > 10 个文件
2. 本轮零验证痕迹：没跑测试、没验制品、没查闭环、没读 `phase-gates.md`

**单轮最多打回 1 次**，避免死循环。全局绕过：`MORROW_GUARD_BYPASS=1`。

安装：`node scripts/install-hook.mjs`（幂等，保留既有 hook，改动前自动备份）。
卸载：`node scripts/uninstall-hook.mjs`。审计日志：`audit.log`。
